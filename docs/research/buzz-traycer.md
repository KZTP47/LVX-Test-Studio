# Buzz and Traycer: source research for LVX Agent Studio

Research date: 2026-10-25. Buzz pinned to `d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66`; Traycer pinned to `efda2734a0d9d9bd547ce2a51e0a19013326e2e4`. GitHub connector metadata confirmed both repositories, then whole shallow source checkouts enabled code-level inspection. No packages were installed, external repository scripts executed, provider sessions started, credentials or private chats read, or memory vaults used. This is static source evidence, not a claim that either app was run successfully.

The useful combination is Buzz's explicit event/session/queue mechanics and Traycer's honest capability contracts and communication graph. Neither repository proves the complete requested combination of native Codex, Gemini and Claude subscription sessions with unrestricted two-way terminal communication. The Studio should keep native sessions intact and add a transparent local routing and observation layer.

## What the two projects actually contain

Buzz is a Rust collaboration platform. Its relay authenticates and verifies signed Nostr events, persists them, fans them out and invokes workflows. A separate `buzz-acp` service admits mentions from that relay, creates ACP sessions in child processes and lets the agent reply through Buzz CLI. The social identity, durable message event, native process and provider session are distinct layers. Introducing its full Postgres/Redis relay architecture would be excessive for one local Electron workspace, but the separations are valuable. See [architecture](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/ARCHITECTURE.md#L145-L170) and [ACP connection contract](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/README.md#L7-L18).

Traycer's public checkout is explicitly **clients, CLI and protocol**, with Host and cloud backends absent. Its Electron shell, React GUI, protocol schemas, graph projections, subscription manager and command client code can be studied; its actual provider orchestration, storage broker and context-conversion internals cannot. The CLI normally provisions a signed Host binary, and the development guide says production releases come from an internal repository. A public interface describing a behavior is weaker evidence than its missing implementation. See [scope boundary](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/AGENTS.md#L1-L24) and [development guide](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/docs/DEVELOPMENT.md#L21-L46).

## Native subscription and communication caveats

Buzz's pinned ACP README documents `codex-acp` with `OPENAI_API_KEY` and explicitly contrasts it with a ChatGPT subscription; the Claude adapter example uses `ANTHROPIC_API_KEY`. That documents this integration's assumptions. It does not establish what every future adapter or provider CLI supports. It also means copying Buzz's launch configuration would not satisfy the requirement to use existing native subscription sessions. See [documented launch paths](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/README.md#L80-L107).

Traycer distinguishes GUI sessions, driven by SDK/JSON-RPC, from interactive CLI sessions in a real PTY. More importantly, `canUseA2ATools` and `canReceiveA2AMessages` are separate predicates. GUI targets receive both capabilities. Claude, Codex and OpenCode terminals get outbound tools, while only Claude terminals have an unsolicited inbound transport. The source explains that accepting durable inbox rows for an agent without a receiver would strand messages forever. Its test matrix corroborates the asymmetry. Gemini is absent from the GUI and TUI rosters inspected here; this is a scoped source observation, not proof that Gemini cannot be integrated independently. See [capability implementation](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/agent/shared.ts#L242-L292) and [explicit regression matrix](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/agent/__tests__/a2a-capability.test.ts#L8-L104).

For LVX, queued **next-turn continuation after idle** is a practical direct-communication mechanism that need not claim mid-turn injection. Each provider adapter should advertise native resume, structured events, next-turn delivery, same-turn steering, transcript access and permission interaction independently. Unsupported functionality should be a visible capability or blocker. A missing login must never cause an automatic switch to API-key billing.

## Session identity and context quality

Buzz derives `SessionScope` once when an event is admitted. That resolved scope keys provider sessions, queues, in-flight tracking and context gathering. Its optional thread policy uses a canonical root; DMs stay conversation-scoped, while channel scope remains the default. This prevents the batch's last message from accidentally redefining a context boundary. Its `AgentPool` separately records session ownership and a monotonic generation, even while a worker is busy and its session state is temporarily checked out. See [scope derivation](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/scope.rs#L1-L80) and [affinity/generation fence](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/pool.rs#L364-L386).

Traycer likewise separates its durable `tuiAgentId` from the provider's `harnessSessionId`. The first Codex launch can return a null provider ID until `thread/started` supplies it; a later observation backfills the record. A tab therefore cannot be identified merely by a process ID or its displayed title. The launch contract also binds profile, actual working directory and all busy worktree paths. See [native launch identity](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/agent/tui/unary-schemas.ts#L48-L145).

A Studio node should persist its own stable agent ID, validated workspace ID/cwd, provider, native resumable session ID, process generation, exact launch settings and capability snapshot. Canvas selection and component remounting should never own process lifetime. One active native turn per session prevents two incoming peer messages from racing two incompatible resumes.

Buzz tracks exact event IDs already delivered to the current provider session. It fetches only the relevant thread/DM history, removes exact duplicates, and commits hydration and delivery state after protocol success. It invalidates that state with session rotation. Its semantic framing preserves standing instruction bodies verbatim while escaping untrusted text embedded in boundaries. These are useful ways to avoid quality decay through duplicate context and accidental prompt rewriting. See [delivery preparation](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/pool.rs#L3013-L3103), [commit and rotation](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/pool.rs#L3402-L3448) and [framing helpers](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/prompt_framing.rs#L1-L44).

For LVX, preserve the native provider's context as the primary execution context. Forward full original assistant text between explicitly linked agents, with source/correlation metadata stored separately. Do not replace text with a central summary, prepend forced planning roles or mutate provider configuration behind the user. Full presentation history is not equivalent to a resumable native context: Traycer explicitly places opaque session anchors outside the presentation record. Its marketing claim of shared context cannot be independently traced through the unavailable Host. See [presentation/session partition](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/persistence/chat-sync/open-harness.ts#L29-L89). Provider switching should be an explicit handoff/fork or a new-turn settings change, retaining the source session; [run-settings semantics](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/agent/gui/subscribe.ts#L1120-L1130) expressly prevent model/harness late-binding into an accepted turn.

## Direct messages, queues and crash recovery

Buzz's queue is not an unbounded mailbox: it caps a scope and whole channel at 500 pending events, batches at 50, and retries at 10 with exponential backoff. Exhaustion returns a dead-letter batch. Overflow can drop queued events, which is a policy LVX should avoid copying silently. A durable inbox can retain the original payload and explicitly reject admission or apply backpressure instead. The requeue mechanism preserves event order and original receive timestamps, which matters for fairness. See [queue bounds](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/queue.rs#L27-L97) and [retry/dead-letter implementation](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/queue.rs#L697-L770).

Its frame writer also handles a subtle failure: cancellation midway through an NDJSON write closes the owned stdin writer; it does not append a cancellation frame to a partial JSON fragment and hope the stream recovers. A CJS adapter needs the same serialized-frame/failed-transport discipline if using structured provider protocols. See [write ownership](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/acp_frame_writer.rs#L1-L25).

Traycer's `agent.sendMessage` is fire-and-forget enqueue, with an optional expected reply tracked by `responseId`. The receiver sends a separate correlated reply; follow-up requests can reuse the same sender-to-receiver thread. Cross-host receivers are explicitly rejected even if agent records are visible across hosts. This demonstrates why discovery, enqueue, transport acceptance, reply and task completion cannot share one success flag. See [message/reply contract](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/agent/shared.ts#L874-L930).

The public inbox protocol adds durable `eventId` and explicit ack after surfacing. Older monitors receive a weaker server-side compatibility ack. A full-inbox read path exists because terminal rendering can truncate large bodies, and the newer version pages them. These are contract-level guarantees; the missing Host storage implementation was not verified. At-least-once inbox replay also does not make a provider's file mutations idempotent. After a crash between native turn acceptance and local result persistence, show an unknown/reconciliation state rather than blindly resubmitting a non-idempotent turn. See [ack compatibility](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/agent/inbox.ts#L276-L288) and [ack contract](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/agent/inbox.ts#L514-L539).

For direct peers, store sender/recipient IDs, source assistant event, original text/hash, correlation/reply ID, generation, delivery state and attempt metadata. Enabled links can route the completed original assistant response to each peer's next idle turn. Bound automatic hops per run and let the user pause, stop, inspect or manually continue. A route is authorization to relay within that configured workflow; it is not proof of delivery. Buzz's own default author gate is owner-only, so peer membership alone would not make its ordinary agents converse. See [inbound author policy](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/README.md#L140-L210).

## A graph backed by real, inspectable conversations

Traycer contains the most immediately useful visual implementation. `CommGraphCanvas` uses ReactFlow with actual agent nodes, observed A2A pair edges, a playback cursor, source jumps, pair details and agent details. Layout uses all agents so replay does not constantly rearrange the graph. The projection keeps the raw event array intact, aggregates one visual edge per unordered agent pair, and shows unanswered reply threads. Parent lineage is only a layout hint, avoiding a line that falsely implies communication. See [canvas](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/clients/gui-app/src/components/epic-canvas/comm-graph/comm-graph-canvas.tsx#L1-L115) and [projection](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/clients/gui-app/src/lib/comm-graph/comm-graph-model.ts#L1-L137).

The graph protocol describes an append-only SQLite event log whose row ID is the replay cursor. Persist first, then wake subscribers. The emitter is a notification mechanism rather than the history source. Snapshot versus event frames is only transport batching: a later event can be old backlog, and snapshot completion is not automatically catch-up. Unknown unrepresentable kinds may be skipped, so this contract's exactly-once statement has a documented representability exception. Causal reply state uses host-local order rather than wall clock. The Studio can simplify to one local host but should retain monotonic sequencing and explicit event versions. See [graph delivery contract](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/epic/communication-graph.ts#L1-L105).

The subscription manager retains events/cursors when a component detaches, fences callbacks by generation, distinguishes unreachable from connecting and bounds construction retries. These details prevent UI lifecycle from restarting or losing a native conversation. Buzz's observer bus is useful for structured live telemetry but its 1,000-event buffer is only RAM, so it cannot replace durable Studio history. See [subscription lifecycle](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/clients/gui-app/src/lib/comm-graph/comm-graph-subscription.ts#L1-L42) and [observer implementation](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/observer.rs#L1-L139).

LVX should distinguish desired route/dependency edges from observed communication edges. Clicking an observed edge should reveal full chronological bodies, sender/recipient, original source and current delivery status. Clicking a node should open its actual live transcript/native session, cwd, provider capability and permission state. A blinking line is not evidence that a provider received the message.

## Quality, planning, review and permissions

Buzz's base prompt asks for visible work, actual source inspection, state-specific evidence, appropriate verification and a fresh review. These are sensible behavioral instructions, but they are not mechanical acceptance checks. Its isolated task runner represents `max_tokens`, `max_turn_requests` and `refusal` as `Completed(reason)`. This is a process/protocol terminal outcome, not proof that useful work or the user's task finished. The workflow engine returns suspension tokens and leaves durable approval recording/resumption to the caller; a persistence TODO remains in the executor. Neither a plan schema nor an approval token proves an enforced end-to-end quality workflow. See [quality instructions](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/base_prompt.md#L117-L133), [isolated outcomes](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/isolated_execution.rs#L1-L96) and [approval suspension](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-workflow/src/executor.rs#L725-L743).

Track transport state separately from semantic outcome and acceptance. A provider can be completed while a task remains refused, truncated, waiting for permissions, failed checks or pending independent review. Explicit reviewer nodes can receive the original work and return direct feedback. Attach plans/check artifacts and exact command/exit/work-state evidence when requested, without forcing a weaker central prompt over the native agent. Traycer's plan fetch schema exposes source, status, hash and missing-blob state, a useful artifact pattern but not hidden-host verification. See [plan response](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/agent/gui/unary-schemas.ts#L332-L353).

Do not copy Buzz ACP's automatic `allow_once` permission selection or generated provider configuration. Preserve the user's native CLI permission mode and surface permission pauses honestly. Traycer's public catalog separately reports supported modes and says the Host rejects unsupported modes, but that Host enforcement is unavailable to inspect. Electron's renderer should stay isolated with a narrow preload bridge; Traycer's actual shell sets context isolation, disables Node integration and enables the Chromium sandbox. Main/CJS should own spawning, workspace validation, stdin and child-tree cleanup. See [automatic permission handling](https://github.com/KZTP47/buzz/blob/d97f6b4c6ed616be0c3f1eb0e13d1eaa9e338a66/crates/buzz-acp/src/acp.rs#L2005-L2088), [mode capability contract](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/protocol/src/host/agent/gui/unary-schemas.ts#L22-L75) and [Electron window preferences](https://github.com/KZTP47/traycer/blob/efda2734a0d9d9bd547ce2a51e0a19013326e2e4/clients/desktop/src/electron-main/windows/window-factory.ts#L104-L122).

## Implementation order and decisive checks

1. Build main-owned native adapters and independently prove genuine execute/resume for each provider. Keep original messages, native login and permission behavior. Declare any missing Gemini/CLI feature honestly.
2. Persist workspace/agent/native-session identity and generation, with serialized per-agent turns. Check that simultaneous peer messages cannot start two resumes or cross workspaces.
3. Add durable inbox/outbox/events before routing. Test restart before launch, after native acceptance and after response storage. Preserve uncertainty where exactly-once execution cannot be proven.
4. Route full assistant text to idle linked peers with provenance, deduplication, bounded hops and pause/stop. Check source/receiver payload hashes and show queued/started/provider-completed/blocked separately.
5. Draw observed event-backed edges with exact-message detail and node-linked chat. Test remount/reopen/reconnect against the same durable cursor/session, and distinguish planned links from observed traffic.
6. Add explicit plan/check/review artifacts and separate acceptance, then improve visual playback and model handoffs. Never interpret refusal or token exhaustion as accepted work.

These checks exercise actual failure boundaries rather than merely testing that a visual node or JSON record exists. Native sessions are the quality-preserving core; the graph and message bus provide visibility and coordination around them.
